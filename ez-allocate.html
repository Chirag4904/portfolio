ENGINEERING CASE STUDY / 03 · 2023

Teaching hours.
Without the guesswork.

EZ-Allocate / Faculty workload allocation

We built EZ-Allocate in college to address a real allocation problem: turning faculty preferences and course requirements into teaching assignments that respect workload limits.

View on GitHub ↗COLLEGE TEAM PROJECT / 2023
PROJECT CONTEXT Real college workflow · DevOps specialization · Microservices & background processing
01 / THE PROBLEM

An assignment is more
than a name in a sheet.

Coordinators need to balance what faculty want to teach with how many hours each course needs—and how much each teacher can take on.

Lecture, tutorial, and practical hours have separate requirements. Those hours can be split across teachers, making spreadsheet-based tracking easy to get wrong.

Our dashboard brings preferences, assignments, and remaining capacity together. Coordinators make the decisions; the backend checks the rules before accepting an assignment.

WORKLOAD

Keep teaching loads in bounds.

Check proposed hours against each teacher’s remaining capacity, using a configurable workload cap.

COURSE REQUIREMENTS

Account for each kind of hour.

Validate lecture, tutorial, and practical allocations separately against the subject’s available hours.

PREFERENCES

Make the context visible.

Show faculty preferences alongside subjects so coordinators can make informed assignments and export the final report.

02 / SERVICE BOUNDARIES

A real problem.
A deliberate learning goal.

Our DevOps specialization shaped the architecture. We chose separate services to apply what we were learning about authentication across services, container deployment, and asynchronous workers while solving a practical college problem.

AUTHENTICATION

Sign once. Verify locally.

Node.js signs tokens with a private key. Django verifies them using the public key, so it does not need to call the auth service on every request.

APPLICATION LOGIC

Keep rules in the API.

Django REST Framework serializers validate workload and subject-hour limits, keeping checks in the backend rather than relying on the UI alone.

DEPLOYMENT

Run services independently.

Docker Compose coordinates the application services, databases, queue, and worker. The API and Celery worker share backend code but run as separate processes.

THE TRADE-OFF

Separate services add deployment, data, and authentication complexity. That was an intentional learning choice for our DevOps specialization. For a small team focused only on shipping this workflow, a single Django application with a background worker could be a simpler starting point.

03 / BACKGROUND WORK

Request the report.
Let a worker prepare it.

CSV generation runs outside the web request. The frontend receives a task ID, checks progress, and offers the download once the worker finishes.

  1. Accept the request

    Django enqueues an export task and returns its ID instead of making the request wait for the entire report.

  2. Generate in the background

    A Celery worker takes the task from Redis, builds the CSV, and saves the generated file in the database. Task results are tracked through Redis.

  3. Deliver the file

    The frontend polls for completion, then follows the result to the download endpoint. Both subject-based and teacher-based reports use this pattern.

WHAT THIS PROJECT REPRESENTS

Early experience.
Practical foundations.

EZ-Allocate brought a real college workflow together with our DevOps coursework: modelling constraints, connecting services, and moving report generation into workers. It is an early example of the backend and asynchronous-system problems I continued working on in later projects.
